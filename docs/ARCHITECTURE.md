## Problem Statement

The firm (TCIA — trade credit and AR protection brokerage) maintains a dedicated **"Prospecting" pipeline** in HubSpot containing seven kinds of high-intent prospects (all qualified + verified leads with prior interest expression). Current quantities in the pipeline as of 2026-05-14:

- **`former_client`** (216) — companies the firm has worked with before but who currently aren't placed with the firm.
- **`bor_target`** (14) — companies known to currently hold a policy with another broker (Broker-of-Record candidates).
- **`coi_referral`** (6) — Center-of-Influence introductions (accountant, attorney, peer broker) whose contacts have expressed credit-insurance interest.
- **`lost_opportunity`** (6) — companies the firm previously quoted but who didn't close at the time.
- **`industry_trigger`** (2) — companies surfaced via industry-driven trigger event (e.g., sector stress signal); expressed interest in evaluating coverage.
- **`conference`** (1) — companies met at a specific event whose decision-maker expressed interest.
- **`bankruptcy_trigger`** (0) — former cold-call targets who expressed interest but didn't close; surfaced when a credit event (bankruptcy in their sector/customer base) makes timing acute.

Total Prospecting pipeline: 245 deals. Funnels excluded from this tool's scope (handled by separate processes): **Renewal** (24 deals — active policies up for renewal), **Active Client** (1 — current placed clients). These live in different HubSpot pipelines/views.

Today, no automated system surfaces these pipeline deals at the right moment for re-engagement. The user (an SDR with decision-maker authority) runs a manual 3–6 month general outreach cadence delivering 100-word, current-event-anchored, value-first emails with low/no-pressure CTAs followed by phone calls. The manual cadence works (one personally-attributed close from a reactivated lost-quote in the last 12 months) but is inconsistent and misses high-leverage moments — specifically, the 60-day window before a prospect's policy renewal, when buyers are actively shopping.

Build an internal automation that:
1. Replaces the manual 3–6 month general cadence with a scheduled queue (~2–3 emails per working day, evenly distributed across the Prospecting pipeline).
2. Adds a sharper trigger: 60 days before estimated renewal date (when known), surface the prospect with appropriate framing.
3. For each surfaced prospect, the local LLM produces **three artifacts** via the canonical prompt in `prompts/draft-pipeline.txt`:
   - **HubSpot Deal Note** — plain-text SDR brief: prospect type, known contacts, decision-maker gap, intel (news/leadership/industry signal, relationship anchor), recommended approach.
   - **Email Draft** — 2 subject options + 4-paragraph body (~150–200 words) in TCIA house voice with relationship-anchor logic, trade-credit-specific phrasing (*"shore up credit management," "ensure AR stays an asset," "leveraging every single carrier and AR resource"*), prospect-type-aware framing, and a soft CTA from the approved list.
   - **Cold Call Opening Script** — opening, context bridge, observation, open question, objection bridges.
4. Auto-creates a paired HubSpot phone-call task due 1–2 days after each email send, with the call script populated into `hs_task_body`.
5. Writes the deal note to HubSpot as a note engagement associated to the deal.
6. Enriches missing contacts via ZoomInfo (when deals lack associated contacts in HubSpot — common for older pipeline deals where the original buyer has moved on).
7. Lets the SDR review one card at a time (all 3 artifacts visible + editable) and click Send / Skip / Edit & Send.

The architecture must be implementation-ready and run inside the firm's existing self-hosted infrastructure (n8n, OpenClaw, local LLM server).

## Approaches Considered

### Approach A: "Sheet + send" (minimal viable)
Single Python script on cron → LLM → Google Sheet. SDR copies/pastes manually, creates phone tasks by hand. Effort: S (~2 days). Rejected: manual phone-task creation will erode adoption after week 2; doesn't fit existing infra intent.

### Approach B: "Full local pipeline" (RECOMMENDED — locked)
n8n daily workflow + local LLM + minimal localhost review UI + auto phone-task creation + OpenClaw monitoring. Effort: M (~1–2 weeks). Selected: matches existing infrastructure, eliminates adoption friction, ships GitHub-ready architecture.

### Approach C: "Inbox-native drafts" (lateral)
Same backend, drafts land in email client Drafts folder via Gmail/Graph API. Effort: M (~1 week). Rejected: webhook reliability + Drafts-folder ergonomics risk after week 2.

### Module breakdown

#### Module 1: Scheduler (n8n workflow `sdr-scheduler`)

**Trigger**: Cron, daily at 06:00 local time.

**Query (HubSpot CRM Search API, batched, single call)**:

```
POST /crm/v3/objects/deals/search
{
  "filterGroups": [{"filters": [
    {"propertyName": "pipeline", "operator": "EQ",
     "value": "${HUBSPOT_PROSPECTING_PIPELINE_ID}"},
    {"propertyName": "notes_last_contacted_date", "operator": "LT",
     "value": <now - 90 days, epoch ms>}
  ]}],
  "properties": ["dealname","amount","createdate","closedate",
                 "renewal_date","hs_lastmodifieddate",
                 "${HUBSPOT_PROSPECT_TYPE_PROPERTY}",  // P20 — env-parameterized
                 "dealstage"],                          // also a candidate type-marker
  "associations": ["contacts","companies"],
  "limit": 200
}
```

Paginate with `after` cursor until exhausted. Stays under HubSpot's 100 req / 10s burst limit.

**Prospect-type classification (per deal)**: HubSpot custom multi-checkbox property `funnel_type` (env var `HUBSPOT_PROSPECT_TYPE_PROPERTY=funnel_type`). HubSpot's API returns multi-checkbox values as a **semicolon-separated string** (e.g., `"former_client;bor_target"`).

Parsing logic:
1. Read `funnel_type` from the deal, split on `;`, trim whitespace, filter to known values.
2. If the result is empty (property missing/null/unknown values) → **drop the deal**, log to `dropped` with `reason = "missing_prospect_type"`. Recoverable per A11 — re-eligible on next run when backfilled.
3. If the result has one value → that's `prospect_type`.
4. If the result has multiple values → apply the **priority order** below to pick the warmest framing:

| Priority | Value | Variant | Why this priority |
|----------|-------|---------|-------------------|
| 1 | `former_client` | structured_re_engagement | Strongest prior relationship → highest-value framing |
| 2 | `lost_opportunity` | structured_re_engagement | Direct prior quote conversation |
| 3 | `bor_target` | structured_re_engagement | Known to have current coverage; soft-touch framing |
| 4 | `coi_referral` | warm_direct_ask | Trusted introducer present in anchor |
| 5 | `bankruptcy_trigger` | warm_direct_ask | Specific credit-event trigger |
| 6 | `industry_trigger` | warm_direct_ask | Sector-driven trigger |
| 7 | `conference` | warm_direct_ask | Event-based memory anchor |

Store the full original list in queue column `funnel_types_all TEXT` (JSON array) for analytics — useful to see how often multi-tag occurs and which combinations convert. Do NOT default to a guessed type — wrong-type framing damages the relationship faster than no framing.

**Contact selection rule**: For each deal, pick the contact in this priority order. The result also sets `contact_source` for the queue row:
1. Contact associated with `associationtype = primary` on the deal → set `contact_source = 'existing'`.
2. If no primary, first contact with `hs_email_optout = false` AND `hs_email_bad_address = false`, sorted by `createdate` desc → set `contact_source = 'existing'`.
3. If no contacts associated at all → tag item with `needs_enrichment = true` and **route to Module 2.5 (ZoomInfo enrichment)** AFTER Module 2's still-in-business check. Many Prospecting pipeline deals from years past have no associated contact because the original buyer moved on; the current CFO / credit manager is likely a new person. Enrichment is the path, not a drop.
4. If Module 2.5 returns a match → use the enriched contact (now created in HubSpot) → set `contact_source = 'zoominfo_enriched'`.
5. If enrichment fails → drop deal, log to `dropped` table with `reason = "no_valid_contact_after_enrichment"`.

**Flow ordering note**: Module 1 emits items tagged `needs_enrichment: bool`. Module 2 runs on all items. Module 2.5 runs only on Module 2 survivors with `needs_enrichment = true`. Module 3 runs on all survivors (enriched or not).

**Compliance filter (HARD, before enqueue)**: Drop any contact where `hs_email_optout = true`, `hs_email_bad_address = true`, or `hs_email_quarantined = true`. Never enqueue. This applies to both pre-existing AND ZoomInfo-enriched contacts (newly enriched contacts default to no opt-out, but if they later opt out, the cooldown applies on subsequent runs).

**Dedupe / cooldown check (join SQLite)**: For each candidate deal_id, skip if EITHER:
- Already exists in `queue` with `status IN ('pending','sent','edit-sent')` within last 30 days, OR
- Exists in `queue` with `status = 'skipped'` and `actioned_at > now - 30 days` (skip-cooldown), OR
- Exists in `dropped` and `dropped_at > now - 90 days`.

**Bucket classification**:
- **Sharp bucket** (if `renewal_date` populated): compute `target_send_date = renewal_date − 60 days`. If `target_send_date` falls in next 7 days → enqueue.
- **Round-robin bucket** (if `renewal_date` empty): assign deterministic year-long slot based on `int(md5(deal_id).hexdigest()[:8], 16) % WORKING_DAYS_PER_YEAR`. If today's working-day index matches → enqueue.

**Working-day index**: Computed from Jan 1 of current year, excluding weekends and a configurable US holiday list (`config/holidays.json`, hand-edited annually).

**Rate cap**: `DAILY_SEND_CAP = 3`. Sharp bucket has priority; if sharp items exceed cap, round-robin items *that overflowed for that day* are deferred to the next working day. Only overflow items defer — the year-long hash-based slot allocation itself is never re-hashed. Deferral is per-day overflow handling, not a reshuffle of the book. Small natural drift accepted in exchange for cap compliance.

**Day-1 bootstrap**: On first run, ingest all eligible deals from the Prospecting pipeline, classify by `prospect_type`, and enqueue only those whose slot matches today's working-day index (or whose sharp renewal window is open). The deterministic hash ensures stable allocation across reboots.

**Output**: list of `{deal_id, contact_id, company_id, send_reason: "renewal" | "round-robin"}` passed to Module 2.

#### Module 2: Still-in-business filter (n8n node + Apollo) — search-only, no enrichment

For each enqueued item, use Apollo's **search** endpoint (does NOT consume enrichment credits per TCIA's existing convention):

1. Call `apollo_mixed_companies_search` with `q_organization_domains: [domain]` (1 result). This is a search, not an enrich — returns basic existence + URL data without burning enrichment credits.
2. If the company doesn't appear in the search response → mark as candidate-for-drop.
3. Secondary verification: HTTP HEAD on `https://<company_domain>`. 200/301/302 = exists. Two consecutive failures (timeout, 404, no DNS) = dead.
4. Drop the deal if BOTH (a) Apollo search returned no match AND (b) HTTP HEAD fails twice. Log to `dropped` with `reason = "inactive_company"` (90-day cooldown — not recoverable without manual intervention).

Apollo's role here is narrow: **company URL verification only**, no contact-level data and no enrichment credit consumption. This matches TCIA's existing Apollo usage convention — Apollo for company URLs + verification, ZoomInfo for people. Contact-level work belongs to ZoomInfo (Module 2.5).

Pass survivors to Module 2.5 (if contact missing) or directly to Module 3 (if contact already valid).

#### Module 2.5: Contact enrichment (n8n node + ZoomInfo) — NEW

**Triggered for**: deals that survived Module 2 but lack any associated contact (per Module 1's contact selection rule, step 3).

**Pre-check (caching)**: Query SQLite `enrichment_cache` table for this `company_id`. If a successful enrichment exists within 90 days → reuse the contact. If a failed enrichment exists within 90 days → skip immediately (don't repeatedly query ZoomInfo for unfindable companies). Otherwise proceed.

**Two-step flow — search first (cheap), enrich only when qualified (credit-burning)**:

This matches TCIA's existing convention with ZoomInfo: search to verify, enrich only when the candidate is qualified.

**Step A — Search (no credit cost on full enrichment)**: call `zoominfo_search_contacts` with:

```
search criteria:
  company_domain: <from HubSpot company record>
  OR company_name: <fallback if domain match fails>
  country: "United States"           # USA-only — TCIA outreach scope (CAN-SPAM only)
  job_titles_any_of: configurable list, default:
    - "Chief Financial Officer"
    - "CFO"
    - "Credit Manager"
    - "Director of Finance"
    - "VP Finance"
    - "Controller"
    - "VP, Risk Management"
  active_only: true
  limit: 3
```

The search returns candidate records (name, title, company, match confidence) WITHOUT consuming a full-enrichment credit on each candidate.

**Step B — Qualification gate (no credit cost)**: filter the candidates locally:
1. Drop any candidate whose `country` doesn't resolve to United States (even if the company is US-HQ, the person may be at an international subsidiary).
2. Drop any candidate whose title isn't in the target list.
3. Rank surviving candidates by tie-break order: CFO > VP Finance > Director of Finance > Controller > Credit Manager > Risk Management.
4. Pick the top-1 candidate.
5. If zero candidates survive qualification → mark `dropped` with `reason = "no_qualified_contact_at_company"` (non-recoverable per A11; 90-day cooldown).

**Step C — Enrich (credit-burning, ONLY for the chosen candidate)**: call `zoominfo_enrich_contacts` on the single top-1 candidate to retrieve the verified email address + full contact details. This is where the credit is spent — once per surviving deal, not per candidate.

**Step D — HubSpot writes (atomic per A2 — cache-first ordering)**:
1. Write `enrichment_cache` row `(company_id, contact_id=null, status='in_progress', source='zoominfo')` BEFORE any HubSpot writes (per A2).
2. Create contact: `POST /crm/v3/objects/contacts` with `email`, `firstname`, `lastname`, `jobtitle`, `enrichment_source = "ZoomInfo {YYYY-MM-DD}"`, `enrichment_confidence`.
3. Associate contact ↔ company.
4. Associate contact ↔ deal.
5. Update `enrichment_cache` row to `(contact_id=<id>, status='success', confidence)`.

If any HubSpot step fails: attempt rollback (delete contact if created). If rollback itself fails, mark cache row `status='orphan'` for manual cleanup (per A2). OpenClaw alert fires on `orphan` rows.

**Compliance gate (per Open Q #8 resolution 2026-05-14)**: TCIA's compliance posture is USA-only outreach. Step A hard-filters `country: "United States"`; Step B re-verifies at qualification time. Document this in `tests/test_compliance.py`. CAN-SPAM compliance (footer + unsubscribe) is handled by HubSpot's engagement API automatically.

**Pick logic**: Highest match-confidence result with a valid email AND a title in the target list. Tie-break: prefer CFO > VP Finance > Director of Finance > Controller > Credit Manager > Risk Management.

**HubSpot writes (atomic — succeed all or rollback)**:
1. Create contact: `POST /crm/v3/objects/contacts` with `email`, `firstname`, `lastname`, `jobtitle`, custom property `enrichment_source = "ZoomInfo {YYYY-MM-DD}"`, `enrichment_confidence = <ZoomInfo confidence score>`.
2. Associate contact ↔ company: `PUT /crm/v3/objects/contacts/{contactId}/associations/companies/{companyId}/contact_to_company`.
3. Associate contact ↔ deal: `PUT /crm/v3/objects/contacts/{contactId}/associations/deals/{dealId}/contact_to_deal`.
4. Write to `enrichment_cache` table: `{company_id, contact_id, source: "zoominfo", confidence, enriched_at}`.

If any step fails, delete the contact (if created) and write a failed-attempt row to `enrichment_cache` with 90-day TTL. Log to OpenClaw.

**On successful enrichment**, set `contact_source = 'zoominfo_enriched'` on the in-flight item. This propagates to the queue row (Module 5) and into the LLM prompt (Module 4) so the email tone shifts slightly more formal.

**Edge case**: if the company itself is not in HubSpot (rare for Prospecting pipeline deals since the deal IS associated to a company, but possible for force-enqueued deals), Module 2.5 cannot create an association. Log to `dropped` with `reason = "company_not_in_hubspot"`. Company creation is out of scope for v1; user creates the company record manually if they want this deal in.

**Cost discipline**: ZoomInfo credits are real money. Module 1 should batch all enrichment-needing deals, then Module 2.5 fires once per scheduler run with a hard cap (`MAX_ENRICHMENTS_PER_DAY = 10`, configurable). If more than 10 deals need enrichment in a day, defer the excess to the next run (with cache writes preventing re-query waste).

Pass enriched survivors to Module 3.

#### Module 3: Enrichment (n8n nodes)

For each survivor, gather:

- **HubSpot deal context**: `amount` (→ quote_amount), `dealname` or custom product property (→ product_line), `createdate` (→ quote_date, formatted as "March 2024" human-readable). Plus last 3 engagements: GET `/crm/v3/objects/deals/{id}/associations/engagements`, sort by `createdate desc`, take first 3, fetch each engagement body via `/crm/v3/objects/engagements/{id}`, truncate body to 200 chars each.

- **Relationship anchor extraction (NEW)**: Search deal notes + engagement bodies for:
  1. Named past TCIA broker (cross-reference against an internal `config/tcia-brokers.json` roster — e.g. "Tom O'Connell"). First hit wins.
  2. Named internal agency contact (account exec, prior TCIA owner) from `hubspot_owner_id` history on the deal.
  3. Prior TCIA work history with the company (any past quote, policy, recorded touchpoint flagged in notes).
  4. If none → `relationship_anchor = null`. LLM is instructed (per `prompts/draft-pipeline.txt`) to drop the relationship paragraph entirely rather than manufacture one.
  Return as: `{anchor_type: "broker"|"agency_contact"|"prior_work"|null, anchor_name: string|null, anchor_context: string|null}`.

- **OneDrive policy excerpt**: Microsoft Graph search via `/search/query` (KQL) scoped to the policy folder driveId. Returns file metadata only. For first match, download via `/drives/{driveId}/items/{itemId}/content`. For .docx, extract text via `python-docx`; for .pdf, via `pypdf2`; for .txt, read directly. Truncate extracted text to 500 chars. Skip enrichment field if no match (LLM tolerates missing input).

- **Current event hook (TIGHTENED — trade-credit-specific signals only)**: Try in order, stop at first success:
  1. **M&A signal** (90-day window): ZoomInfo `enrich_scoops` (M&A scoop type) or PitchBook free-tier search → company appears in acquisition / divestiture / funding announcement within 90 days. Return event type + counterparty + date.
  2. **Leadership change signal** (90-day window): new CFO, Controller, VP Finance, or Treasurer hire at the company. Source: ZoomInfo `enrich_contacts` filtered by job-start-date < 90 days OR LinkedIn company-page scrape for "promoted to" / "new" / "joins as CFO" / "named Controller".
  3. **Sector financial stress signal**: industry-level (NOT company-level) indicator within 60 days — e.g., rising default rates in the company's NAICS, sector-wide carrier rate hardening, notable peer bankruptcy. Source: a curated `config/sector-signals.json` updated weekly by Daniel, OR an industry-news RSS filtered by sector.
  4. **Fallback `hook_source: "none"`** — no qualifying signal found. Set `hook_text = null`. The prompt's relationship-anchor logic takes over; if neither hook nor anchor resolves, the LLM falls back to a generic value-touch about TCIA's broader carrier panel.

  Generic news search (Google/Bing for any headline) is explicitly OFF the table — generic news rarely connects to credit exposure and dilutes the targeting.

Pass enriched bundles to Module 4 with the full payload: `{deal_id, company_id, contact_id, contact_email, contact_first_name, contact_last_name, company_name, company_acronym (if discoverable from notes), quote_amount, product_line, quote_date_human, renewal_date_or_null, send_reason, prospect_type, policy_excerpt_or_null, hook_text, hook_source, hook_metadata, relationship_anchor (object with anchor_type/anchor_name/anchor_context, or null), contact_source}`.

#### Module 8: OpenClaw monitoring

Watches the n8n workflows (`sdr-scheduler` and `sdr-send`) for:
- Execution failures (LLM down, HubSpot 429, Apollo 401, etc.)
- Queue depth anomalies (zero items enqueued for >2 days; >10 items enqueued in one day)
- Weekly conversion KPI digest (computed via SQL on the queue DB):

```sql
-- Sent count last 7 days
SELECT COUNT(*) FROM queue
  WHERE status IN ('sent','edit-sent') AND actioned_at > date('now','-7 days');

-- Skip rate
SELECT (SELECT COUNT(*) FROM queue WHERE status='skipped' AND actioned_at > date('now','-7 days')) * 1.0
     / (SELECT COUNT(*) FROM queue WHERE status IN ('sent','edit-sent','skipped') AND actioned_at > date('now','-7 days'));

-- Edit ratio
SELECT (SELECT COUNT(*) FROM queue WHERE status='edit-sent' AND actioned_at > date('now','-7 days')) * 1.0
     / (SELECT COUNT(*) FROM queue WHERE status IN ('sent','edit-sent') AND actioned_at > date('now','-7 days'));

-- Dropped count
SELECT COUNT(*) FROM dropped WHERE dropped_at > date('now','-7 days');

-- Per-type touch volume (sanity-check round-robin proportionality)
SELECT prospect_type, COUNT(*) FROM queue
  WHERE status IN ('sent','edit-sent') AND actioned_at > date('now','-7 days')
  GROUP BY prospect_type;

-- Per-contact-source breakdown (existing vs zoominfo_enriched conversion)
SELECT contact_source, status, COUNT(*) FROM queue
  WHERE actioned_at > date('now','-30 days')
  GROUP BY contact_source, status;

-- Enrichment success rate
SELECT
  CAST(SUM(CASE WHEN status='success' THEN 1 ELSE 0 END) AS REAL) / COUNT(*)
FROM enrichment_cache
  WHERE enriched_at > date('now','-30 days');
```

**Phone-task completion read-back** (nightly): query HubSpot tasks via Search API with `hs_task_subject` operator `CONTAINS_TOKEN` value `"reactivation"` (HubSpot Search does not support `LIKE`); for each match, check `hs_task_status`. Cross-reference `hubspot_task_id` from SQLite to scope to tool-created tasks only. Compute completion rate, surface in weekly digest.

**Failed-artifact retry sweep** (nightly): query SQLite for rows where `status IN ('sent','edit-sent')` AND (`hubspot_task_id IS NULL` OR `hubspot_note_id IS NULL`). For each, retry the missing write (task creation or note creation). Backstop for Module 7 partial-success cases.

OpenClaw is the existing monitoring layer — this design adds two new workflow IDs to its watchlist and one nightly cron query; no new OpenClaw infrastructure.

### Cloudflare setup (one-time, ~10 minutes)

1. **Install `cloudflared` on the internal server** (Linux: `curl -L ... -o cloudflared && chmod +x && sudo mv /usr/local/bin/`). Windows: download the MSI from cloudflare.com/downloads.
2. **Authenticate**: `cloudflared tunnel login` — opens browser, pick the `tradecredit.agency` zone.
3. **Create tunnel**: `cloudflared tunnel create sdr-engine`. Note the tunnel UUID — goes into env as `CLOUDFLARE_TUNNEL_UUID`.
4. **Create DNS record**: `cloudflared tunnel route dns sdr-engine sdr.tradecredit.agency` (creates a CNAME pointing to the tunnel).
5. **Tunnel config** at `~/.cloudflared/config.yml`:
   ```yaml
   tunnel: <UUID from step 3>
   credentials-file: /home/<user>/.cloudflared/<UUID>.json
   ingress:
     - hostname: sdr.tradecredit.agency
       service: http://127.0.0.1:5679
     - service: http_status:404
   ```
6. **Run as service**: `sudo cloudflared service install` (Linux uses systemd; auto-starts on boot).
7. **Cloudflare Access policy** (in the Cloudflare dashboard → Zero Trust → Access → Applications):
   - Create "Self-hosted application" for `sdr.tradecredit.agency`
   - Identity providers: One-time PIN to Daniel's email (or wire TCIA's Google Workspace / Microsoft 365 SSO if available — cleaner)
   - Policy: `Include: emails: daniel@tcia.com`. No other policies.
   - Session duration: 24 hours (so Daniel doesn't re-auth every morning).
8. **Test**: from a phone on cellular (NOT firm LAN), visit `https://sdr.tradecredit.agency`. Should prompt for Daniel's email → PIN sent → enter PIN → see queue UI. Any other email → access denied at Cloudflare edge.

This setup means: even if the internal server has a misconfigured firewall or the home network is on a non-static IP, the tunnel keeps working as long as the server has outbound internet.
